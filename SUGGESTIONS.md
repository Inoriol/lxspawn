# Privilege Hardening Suggestions

Review of the sudoers rules generated by `installSudoersRules()` in `cmd/lxspawn/setup.go`. Nothing here has been run against a real sudo yet; items marked **(verify)** need confirming on the Bazzite test machine.

## Summary

The rules are meant to let members of the `lxspawn` group run a fixed set of privileged commands against `/var/lib/machines/*` only. As written, they do not enforce that. Sudoers wildcards behave differently from shell globs, so any `lxspawn` group member can currently reach arbitrary paths and, via `nsenter`, a host root shell.

Until fixed, the honest description of the current model is: **membership in the `lxspawn` group is root-equivalent.**

## Why the current rules are too loose

Sudoers matches the command's whole argument string against a single `fnmatch(3)` pattern, without path semantics:

1. **`*` matches `/`.** It is not limited to one path component.
2. **`*` matches spaces.** A pattern can match several arguments, not one. `rm -rf /var/lib/machines/*` also matches `rm -rf /var/lib/machines/x /etc/foo`.
3. **`..` is not normalized.** `rm -rf /var/lib/machines/../../etc/foo` matches.
4. **Options can be injected** wherever a `*` or `[0-9]*` leaves room after the expected prefix.

Concrete examples against the current rules (all should be denied, none are):

| Rule (setup.go) | Bypass |
|---|---|
| `rm -rf /var/lib/machines/*` (L188) | `rm -rf /var/lib/machines/x /home/victim` or `.../machines/../../etc/x` |
| `chown [0-9]*:[0-9]* /var/lib/machines/*` (L193) | `chown 0:0 /etc/sudoers.d/x /var/lib/machines/x` |
| `chmod [0-7]* /var/lib/machines/*` (L196) | `chmod 4755 /tmp/mybin /var/lib/machines/x` (setuid root) |
| `mv /var/lib/machines/* /var/lib/machines/*` (L199) | `mv /var/lib/machines/x /etc/cron.d/y /var/lib/machines/z` |
| `nsenter -t [0-9]* ... /bin/bash -c *` (L205) | `nsenter -t 1 -m -u -i -n -p -- /bin/bash -c 'anything'`: PID 1 is the host |
| `journalctl -u systemd-nspawn@*.service -n [0-9]* -o short-iso` (L208) | `-n 5 --file=/path/to/journal` appended inside the `[0-9]*` |
| `mkfs.ext4 -q /dev/*/lxspawn-*` (L244) | `mkfs.ext4 -q /dev/sda1 /dev/x/lxspawn-y`: the glob spans the space, so this formats `/dev/sda1` |
| `lvcreate --name lxspawn-* *` (L234) | trailing `*` accepts any further arguments |
| `btrfs subvolume delete /var/lib/machines/*` (L215) | same space/`..` issues |

The `nsenter` rule is the most serious. The README's "PID ownership checks" claim cannot be enforced by sudoers, and checks inside the Go binary do not help because a user can invoke `sudo nsenter` directly.

## Suggested changes, in priority order

### 1. Remove or replace the `nsenter` rule

Sudoers cannot verify that a PID belongs to a container. Options:

- **Replace with machined.** **(verify)** Try `systemd-run -M <name> --pipe --wait -- <cmd>` for non-interactive `system`/`user` provisioning, `exec`, and readiness probes. It goes through `systemd-machined` and polkit, needs no sudo rule, and does not allocate a PTY, so it may avoid the `machinectl shell` PTY errors listed under Known Issues. Test it on a machine whose name contains hyphens and on a freshly booted one (the `no system bus in container` case).
- **If that does not work**, keep `nsenter` and document that the `lxspawn` group is root-equivalent (see item 4). Do not describe the rule as restricted.

### 2. Replace glob arguments with sudoers regex arguments

Sudo 1.9.10 (January 2022) and later can match command arguments with a POSIX extended regular expression when the argument string starts with `^` and ends with `$`. **(verify the exact syntax and quoting with `visudo -c` on the target sudo version.)**

A regex can pin each argument to a single path component:

```
# machine name: one path component, no leading '-' or '.', no '/', no space
%lxspawn ALL=(root) NOPASSWD: /usr/bin/rm ^-rf /var/lib/machines/[a-z0-9][a-z0-9_-]*$
%lxspawn ALL=(root) NOPASSWD: /usr/bin/btrfs ^subvolume delete /var/lib/machines/[a-z0-9][a-z0-9_-]*$
%lxspawn ALL=(root) NOPASSWD: /usr/bin/btrfs ^subvolume snapshot -r /var/lib/machines/[a-z0-9][a-z0-9_-]* /var/lib/machines/[a-z0-9][a-z0-9_-]*/\.snapshots/[a-z0-9][a-z0-9_.-]*$
%lxspawn ALL=(root) NOPASSWD: /usr/bin/chown ^[0-9]+:[0-9]+ /var/lib/machines/[a-z0-9][a-z0-9_-]*$
%lxspawn ALL=(root) NOPASSWD: /usr/bin/chmod ^[0-7]{3,4} /var/lib/machines/[a-z0-9][a-z0-9_-]*$
```

Notes:

- Because `[...]` excludes space and `/`, the multi-argument and `..` bypasses disappear.
- Build the character classes from the same rule the Go code already uses for machine and snapshot name validation, so the two cannot drift. A small generator function in `setup.go` that emits the regex from one constant would do it.
- `chmod` should probably be limited further. Consider whether `4xxx` modes are ever needed; if not, use `^[0-7]{3}` or `^0?[0-7]{3}`.
- `chown -R 0:0` (L192) is only needed for rootfs. Pin it to the machine directory the same way.
- Prefer exact subcommands over a trailing `*`. `lvs --noheadings *` and `lvcreate --name lxspawn-* *` should list the exact flag set the code uses.

### 3. Make the installer safe and strict

- **Validate before installing.** `WriteFileAtomic` writes straight to `/etc/sudoers.d/lxspawn`. A syntax error breaks sudo for every user. Write to a temp file in the same directory, run `visudo -cf <tmp>`, then rename.
- **Check the sudo version.** If `sudo -V` reports older than 1.9.10, either refuse to install the privileged rules or print a clear warning that the group is root-equivalent. Do not silently fall back to glob rules that look restrictive.
- **Check for duplicated lookups.** `findBinary("lvs")` is called twice in the LVM block (L226 and L229); harmless but worth tidying while the block is being rewritten.
- **Resolve binaries once** and pin absolute paths, as the code already does. Keep that.

### 4. Document the actual trust model

Whatever is decided on `nsenter`, say in the README (and remove the duplicated "Privilege Model" section while there):

- What the `lxspawn` group can do without a password.
- Whether that is root-equivalent, as `docker` and `libvirt` group membership is. If any rule can still be abused (as `nsenter` can), say so directly.
- Remove or rewrite "PID ownership checks" in the README's setup description.

### 5. Test the rules, not just the generator

Unit tests on the generated text will not catch bypasses. Add an integration test (CI container or the Bazzite box) that installs the rules for a throwaway user and asserts that these are **denied**:

- `sudo -n rm -rf /var/lib/machines/../../tmp/canary`
- `sudo -n rm -rf /var/lib/machines/x /tmp/canary`
- `sudo -n chmod 4755 /tmp/f /var/lib/machines/x`
- `sudo -n mkfs.ext4 -q /dev/loopN /dev/x/lxspawn-y`
- `sudo -n nsenter -t 1 ...` (once item 1 is decided)

and that the legitimate lifecycle (create, snapshot, rollback, delete) still works. Also run `visudo -c` on the generated file as part of the existing test workflow.

### 6. Group-writable systemd directories make the sudoers work moot (confirmed)

`setup.go:80-92` runs `ensureDir` on `/etc/systemd/nspawn`, `/etc/systemd/system` and `/etc/systemd/system/systemd-nspawn@.service.d`, giving each `root:lxspawn` `0775`. The polkit rule lets the group reload systemd and start any `systemd-nspawn@<name>.service`.

A group member can therefore drop `systemd-nspawn@x.service.d/evil.conf` with `ExecStartPre=+/bin/sh -c '...'` (or an `.nspawn` file with `Bind=/`), run `daemon-reload`, and start it as root. No sudo rule is involved. Hook scripts under `/var/lib/lxspawn/<m>/.hooks` are written by the user and executed as root, so any process running as that user can edit them.

Hardening the sudoers rules (items 1-3) does not change this. One of these must be done as well:
- Make these directories root-owned `0755` and route unit/`.nspawn`/hook writes through a narrow privileged path (a sudoers rule that installs a single validated file, for example).
- Or state clearly that the `lxspawn` group is root-equivalent (item 4) and stop describing the polkit rule as "scoped to lxspawn machines only". It matches by name pattern, not by ownership.

Still to review: the polkit regex itself for anchoring problems (whether `systemd-nspawn@*.service` can match more than a machine name).

## Design note: why not a helper binary

A privileged helper was considered and rejected: it adds a large, separately audited attack surface, and "validated by our own code" is only as strong as that code. The regex-argument approach keeps the privileged surface as plain-text sudoers lines that anyone can read and verify, with no new binary. Calls into systemd (machined, polkit) are preferred where they work reliably; low-level `btrfs`/`rm`/`chown` calls stay where `machinectl` hangs or has no equivalent (for example, creating a btrfs subvolume for a machine).

# Code Review

All P1 (data loss and host compromise), P2 (broken features and wrong behaviour), and P3 (hardening and cleanup) issues from the code review have been fixed. See CHANGELOG.md for details.

## CI, release and dependencies

- Actions are pinned to tags, not commit SHAs.
- `release.yml` has no `needs`/test gate, so a tag publishes untested code.
- No signing, SBOM or `govulncheck`. Add cosign or GPG signing of checksums.
- `.goreleaser.yml` runs `go mod tidy` in `before:`, which can change dependencies at release time. Use `go mod verify` instead.
- `test.yml` runs the suite three times.
- `cockpit/.github/` (including dependabot) is inert because GitHub reads only the root `.github`, so the Go module has no dependency updates. Add a root `dependabot.yml`.
- Dependencies are dated (`cobra 1.8.0`, `x/sys 0.17.0`).

## What is already good

- **State and writes.** `machines.json` is written atomically with mode `0600` under a flock; `WriteFileAtomic` is used consistently, and hook scripts get SELinux labels.
- **Systemd handling.** Start and stop wait on the systemd job result with timeouts rather than fire-and-forget. `Exec` quotes arguments and takes the PID from machined rather than user input.
- **Command construction.** All external commands use argv slices, not shell strings, and binaries are resolved to absolute paths for sudoers. The machine-name regex is anchored and used consistently in Go and polkit.
- **Design.** The snapshot-then-swap rollback, the small storage-backend interface, the warn-and-fall-back-to-directory behaviour for LVM without a thin pool, hash-based skipping of unchanged post-boot scripts, and thorough provision/template/yq tests.

## Template review (`examples/`)

Review of `examples/myserver.yaml` and the 11 templates in `examples/templates/` (adguard, pihole, docker-host, jellyfin, plex, nextcloud, samba, debian-base, ubuntu-base, fedora-base). I read every template; I only skimmed the `.md` files, so the docs are not audited. Nothing was run, since the templates install real software over the network. **(confirmed)** means I checked the claim against the lxspawn source; **(verify)** means it depends on upstream software behaviour that should be tested on a real machine.

Checked and fine: `tasks: infinity` in docker-host is valid because `Tasks` is a string in `config/schema.go:47`; `fedora:44` and `fedora:43` are listed by `list-distros`.

### Cross-cutting problems

**X1. Readiness probes can hang forever (confirmed).** `provision/probe.go:48-82` runs each attempt with `cmd.Run()` and no timeout, and every template probe is written as `until <check>; do sleep 2; done`. If the service never comes up, the script never exits, so the "30 attempts, then print the hint" logic is never reached and `launch` blocks indefinitely. The `hint:` fields in all templates are effectively dead. Fix in two places: wrap each attempt in a context timeout in the engine, and write template probes as single-shot checks (`dig @localhost example.com +short | grep -q .`) so the engine does the retrying.

**X2. The `boot` sections probably do nothing (verify; depends on R11).** Every template starts with a `boot` script that runs `systemctl mask systemd-udevd` and `systemd-modules-load`. If the `lxspawn-boot.service` enable symlink is dangling (R11), none of these run. `fedora-base.yaml` even repeats its `resolv.conf` write in the `system` phase with the comment "after systemd-resolved has started", although the boot phase masks resolved, which looks like a workaround for exactly this. Check in a running container with `systemctl is-masked systemd-udevd` and `systemctl status lxspawn-boot`. Either way, identical masking copied into 11 templates belongs in image post-processing (`internal/image/cleanup.go`), not in each template.

**X3. Unpinned, unverified downloads run as root.** `curl ... | sh` from the AdGuardHome `master` branch (`adguard.yaml:51`), `curl | bash` from `install.pi-hole.net` (`pihole.yaml:65`), Nextcloud `latest.tar.bz2` with no checksum (`nextcloud.yaml:54`), and repository keys fetched without a fingerprint check (docker, jellyfin, plex). Any upstream compromise or a bad `master` commit lands in your container with root. lxspawn already has a `file:` provision source with a SHA256 `digest:` option; use it for the installers and the tarball, pin versions or tags, and publish the expected digests in the template.

**X4. Passwords and secrets.**
- **Defaults are real credentials:** `admin`/`admin`, `nextcloud`/`nextcloud` and `samba`/`samba`, with only a "Change this!" comment. Nothing stops a user launching the template as is.
- **Secrets are logged:** `set -eux` echoes every command, so the `mysql -e "CREATE USER ... IDENTIFIED BY '...'"` and `occ maintenance:install --admin-pass` lines, with the passwords substituted in, go to the provisioning output. They are also visible in `ps` inside the container.
- **No escaping:** `{{.Param.*}}` values are spliced into shell and SQL unescaped, so a password containing `'` breaks the script (R26 covers the missing escaping in the engine).
- **Fix:** have the script refuse to run while a secret still has its default value (`[ "{{.Param.db_pass}}" != nextcloud ] || { echo "set db_pass"; exit 1; }`), or generate a random one and write it to a root-only file inside the container. Use `set +x` around secret-bearing commands.

**X5. Hard-coded LAN assumptions.** `adguard.yaml` and `pihole.yaml` default to `192.168.0.100/101`, gateway `192.168.0.1`, and public upstream DNS `8.8.8.8`/`8.8.4.4` (Fedora uses `8.8.8.8`/`1.1.1.1`). On a different subnet the container comes up with a wrong static address; the default upstreams send every LAN query to Google, which is a surprising default for a privacy-oriented DNS sinkhole. The two files also duplicate the same `10-eth.network` block. Require these as parameters without defaults (see X4), and offer DHCP as the default.

**X6. No `DEBIAN_FRONTEND=noninteractive` anywhere in the repo (confirmed by grep).** Provisioning runs through `nsenter` without a TTY so debconf usually falls back to non-interactive, but package upgrades with config-file prompts or `needrestart` can still stall. Setting it once in the provisioning environment (`buildEnvExport` in `provision/exec.go`) fixes all templates.

**X7. No automated check of the templates.** CI never loads them. Add a test that, for each `examples/templates/*.yaml`, runs the full `config.Parse` + `config.Validate` + template render (with `missingkey=error`, see R26) and runs `shellcheck` over the embedded scripts. Today `lxspawn validate` would also pass them without validating (R10).

### Per-template findings

**Nextcloud (`nextcloud.yaml`)**
- **T1. The data volume is never used (confirmed by reading).** The template bind-mounts the host's `/var/lib/nextcloud` at `/var/www/html/data`, but Nextcloud is unpacked into `/var/www/html/nextcloud` and installed without `--data-dir`, so its data directory is `/var/www/html/nextcloud/data` inside the rootfs. User files therefore live in the container and are deleted by `lxspawn delete`, while the host volume stays empty. Fix: pass `--data-dir /var/www/html/data` and make sure the mount is owned by `www-data`.
- **T2. Access via LAN IP is probably rejected (verify).** `occ maintenance:install` sets `trusted_domains` to `localhost` only, so opening the container's LAN address gives "Access through untrusted domain". Add `occ config:system:set trusted_domains 1 --value=<addr>` (or a param).
- **T3. Not re-runnable.** `CREATE DATABASE` and `CREATE USER` fail on a second run (use `IF NOT EXISTS`), and `occ maintenance:install` fails once installed; guard it with `occ status`. This matters because `lxspawn provision` re-runs changed scripts.
- **T4. Smaller:** the extracted tarball `latest.tar.bz2` is left in `/var/www/html`; `chown -R www-data /var/www/html` recurses into the bind-mounted host directory; plain HTTP only with no TLS or reverse-proxy note; no cron for background jobs.

**AdGuard (`adguard.yaml`)**
- **T5. Launch blocks until the wizard is finished (confirmed via X1, wizard behaviour verify).** `adguard.md` says first-run setup is a web wizard on port 3000. Until it is completed AdGuard Home does not serve DNS, so the `dig @localhost` probe never succeeds and `launch` hangs. Either pre-seed `AdGuardHome.yaml` with a `data` provision (as the Pi-hole template does with `setupVars.conf`), or probe `http://localhost:3000` instead.

**Pi-hole (`pihole.yaml`)**
- **T6. Hard-coded `PIHOLE_INTERFACE=eth0` (verify).** The README's Known Issues say macvlan creates `mv-<interface>` inside the container, and the template's own comment says the interface name is decided by networkd, yet the config pins `eth0`. Pi-hole may bind to a non-existent interface.
- **T7. Pi-hole v6 changed its config model (verify).** Current releases moved to `pihole.toml`; `setupVars.conf` with `WEBPASSWORD` is the v5 mechanism and may only be honoured for migration, so the password may not be applied. Pin the Pi-hole version or check what the unattended installer reads today. The web password also sits in a plaintext file written with the default mode (see the file-mode finding under P3).

**docker-host (`docker-host.yaml`)**
- **T8. Docker does not survive a restart (confirmed).** `dockerd` is started as a background process from the provisioning script. Post-boot provisioning runs only in `Launch` and `Provision` (`manager.go:219-250`, `:629`), not in `Start`, and unchanged scripts are skipped by hash (`engine.go:147-150`). After `lxspawn stop` and `lxspawn start`, Docker is down, and the probe hint points at `journalctl -u docker`, which has no entry. Fix: install a real systemd drop-in for `docker.service` (cgroupfs `daemon.json` is already written) and enable it. The comment claims `systemctl enable` is unreliable; find out why (cgroup delegation? see R11) rather than working around it.
- **T9. Weak isolation, undocumented.** `seccomp: false` plus `CAP_SYS_ADMIN`, `CAP_BPF`, `CAP_NET_ADMIN` and `CAP_NET_RAW` is close to a privileged container. The template and its `.md` should say so. `chmod 666 /var/run/docker.sock` makes every user in the container root-equivalent; use the `docker` group.
- **T10. Host side effects.** The `pre_start` hook permanently sets `net.ipv4.ip_forward=1` and `bridge-nf-call-iptables=1` on the host and loads `br_netfilter`, with no `post_stop` revert. That changes firewall behaviour for every other workload. The `post_start` hook only runs `sleep 2`. Document the host changes or drop them.

**Samba (`samba.yaml`)**
- **T11. Open writable share by default.** `guest ok = yes`, `map to guest = Bad User`, `read only = no` exposes `/data` read-write to the entire LAN with no password. Guests map to `nobody` with no `force user`, and the host directory is created root-owned by the hook, so writes may fail anyway (verify). Default to authenticated access and read-only.
- **T12. Password handling.** `smbpasswd -a nobody` with the password `samba`, errors discarded by `2>/dev/null || true`; `samba.md` instead tells users to create `fileuser`. The two disagree.
- **T13. Probe is mostly meaningless.** Only `samba` and `samba-common-bin` are installed, so `smbclient` does not exist and the first branch of the `||` always fails; the probe passes whenever port 445 is open. Install `smbclient` or probe the port directly.
- **T14. Other:** `CAP_DAC_OVERRIDE` is already in nspawn's default capability set, so it is likely redundant (verify); the template is named `fileserver` while the file and docs say `samba`.

**Jellyfin and Plex (`jellyfin.yaml`, `plex.yaml`)**
- **T15. Failures are swallowed.** `apt-get install ... || true` and `|| echo "... using software decoding"` hide a missing GPU driver, and neither the build nor the probe checks that hardware acceleration works. Run `vainfo` after install and warn loudly (or fail) when it returns nothing.
- **T16. Architecture hard-coded.** `arch=amd64` in the Jellyfin repo line (the Docker template correctly uses `dpkg --print-architecture`). The README advertises ARM Mali/Adreno GPU support, which this breaks.
- **T17. State directories collide with the host.** The volumes use `/var/lib/jellyfin` and `/var/lib/plex` on the host, the same paths a host install would use, and the `pre_start` hook silently creates a mistyped `/mnt/media` as an empty directory instead of failing, which gives an empty library with no error. Use a lxspawn-specific path (`/var/lib/lxspawn-data/{{.Name}}`) and fail if the media directory is missing.
- **T18. Ownership of the state directory (verify).** The hook creates it root-owned; it only works if the package post-install chown acts on the bind mount, which depends on `--private-users=no`.
- **T19. Minor:** `software-properties-common` is unnecessary on Debian and pulls in Python; `rocm-opencl-runtime` is not in bookworm (the comments admit this for the Intel package).

**Base templates (`debian-base`, `ubuntu-base`, `fedora-base`, `myserver.yaml`)**
- **T20. `network: host` is the default in all of them and in the README quick start.** The container shares the host network namespace, so its services bind host ports, and a networkd/resolved running inside can interact with host links (verify what `image/network.go` injects). It is the only rootless mode, but the docs should say that it gives no isolation.
- **T21. Fedora DNS.** The base template replaces `resolv.conf` with public resolvers (`8.8.8.8`, `1.1.1.1`, `8.8.4.4`) twice, ignoring the LAN's DNS (including the Pi-hole this project also ships). Use a `data` provision, make the resolvers a param, and drop the contradictory comment (see X2).
- **T22. `ubuntu-base` runs `apt-get update` twice** and `fedora-base` upgrades everything on every provision, so the first launch is slow and the result changes over time.

## Upstream systemd/nspawn outlook

Researched on 2026-11-10 from systemd's `NEWS` and `TODO.md` plus a GitHub PR/issue search. The search results were truncated (about 10 of 26 matches read) and summarised by a small model, and I did not read systemd's source, so treat "nothing found" as "no evidence", not proof.

**The "nspawn rebuilt on `systemd-executor`" rumour.** `systemd-executor` has existed since v255 as the separate binary PID 1 runs for unit processes. The only trace of an nspawn link is an unscheduled, unassigned `TODO.md` line: "Make nspawn to a frontend for systemd-executor, so that we have two ways into the executor". The direction is nspawn as a frontend to the executor, not the other way round. No PR, issue or `NEWS` entry implements it. It is an internal refactor and does not change the interfaces lxspawn uses (`.nspawn` files, `systemd-nspawn@.service`, machined D-Bus, `machinectl`), so no action is needed. One precaution: keep taking the leader PID from machined (already done) rather than walking `/proc`, in case the process-tree shape changes.

**Changes that can affect lxspawn.**
- **U1. `RestrictAddressFamilies=` default will tighten (v261, opt-in today).** `NEWS` says a future version will restrict containers to IPv4, IPv6 and Unix sockets by default. That would break anything needing netlink or packet sockets: DHCP clients, networkd, Docker (the docker-host template). Fix: add a `security.restrict_address_families` option to `internal/config/schema.go`, emit it from `internal/compiler/nspawn.go` when the host systemd supports it, and set it explicitly in templates that need `AF_NETLINK`/`AF_PACKET`. This is the one small change worth making soon.
- **U2. nftables only (v259).** nspawn and networkd dropped iptables/libiptc, so NAT and port forwarding for `zone`/`private` modes and `ports:` need nftables on the host. Document it, and have `lxspawn setup` warn when nftables is missing.
- **U3. The README's "systemd 245+" is stale.** Replace it with a tested matrix (current Fedora/Bazzite plus the oldest supported release) and extend the version checks in `internal/kernel/systemd.go`.
- **U4. Not affected today:** the v261 rename of `--user` to `--uid=` (lxspawn writes `.nspawn` files and does not pass it) and the v262 change to the `PrivateUsersOwnership=` default (lxspawn defaults to `PrivateUsers=no`/`identity`; it only matters for users who set `private_users: pick`).
- **U5. Possibly related bug (unverified):** systemd issue #41278 (closed) describes sporadic nspawn unit failures where spawning the executor fails with `EBUSY` on cgroup reuse. It may relate to flaky starts; check it if you see intermittent start failures.

**Possible future simplifications (not available on current hosts).**
- `SetCredential=`/`LoadCredential=` in `.nspawn` files (merged October 2026, so v263 at the earliest) could carry template secrets instead of putting them in scripts and logs (see X4).
- `importctl pull-tar` could replace the custom image fetcher and tar extractor; see the next subsection.

### `importctl pull-tar` for image fetching

Researched on 2026-11-10 from systemd's `importctl` man page, `NEWS`, `src/import` and `src/shared/tar-util.c` (main branch), the `images.linuxcontainers.org` directory listing, and lxspawn's own `Create` flow. Verdict: worth doing, but not as a drop-in swap.

**What it does.** `importctl pull-tar URL NAME` (v256 and later; `machinectl pull-tar` is the older spelling, same `systemd-importd` service) downloads, verifies, extracts, and on btrfs creates a subvolume. With `--keep-download=yes` (the default for the `machine` class) it keeps a read-only cache subvolume named after the URL and ETag and snapshots it to the local name, so the second and later machines from the same image are instant and share disk space. importd is a sandboxed root service; on main, tar extraction is done in-process with libarchive on an fd-based tree.

**Fit with the LXC image server.** The server publishes `SHA256SUMS` and `SHA256SUMS.asc` next to each `rootfs.tar.xz`, which is the layout importd expects, so `--verify=checksum` should work as is. `--verify=signature` (the importctl default) needs the server's key in `/etc/systemd/import-pubring.pgp`, and ASCII-armored `.asc` support landed in v258 (by my reading of where it sits in `NEWS`).

**What it would fix.** R5 (symlink-following extraction), R16 (lost uid/gid and setuid bits; today everything ends up `root:root` after the final `chown -R 0:0`), the missing checksum verification, the tmpfs download and the missing decompression cap, plus the fetcher's own `btrfs subvolume create` and `chown` sudo calls.

**Why it is not a drop-in swap.**
- **I1. Root-owned rootfs breaks the current setup flow.** `Manager.Create` (`internal/machine/manager.go:94-216`) fetches into a tree owned by the invoking user, then runs `CleanupRootfs`, `InjectNetworkConfig` and the pre-boot provisioners (`boot`, `data`, `yq`) as that user, and only at the end runs `chown -R 0:0` (`fixRootfsOwnership`, around line 640). importd leaves a root-owned tree, so every one of those host-side writes would need privilege. This is the real blocker, and it is the same problem as R6 (symlinks followed by host-side writes). Whatever replaces it must not resolve paths on the host.
- **I2. Create order and LVM.** importd creates the target itself, so "create storage first, then fetch" stops working, and the LVM thin backend (a mounted volume at the target path) is incompatible. The btrfs and directory backends could work.
- **I3. Wider group privileges.** The polkit action `org.freedesktop.import1.pull` defaults to admin-only, so `lxspawn setup` would have to grant it (and `org.freedesktop.import1.cancel`) to the `lxspawn` group. It is not obviously scoped by URL or name; check before relying on it.
- **I4. Cache growth.** Cached read-only subvolumes accumulate in `/var/lib/machines` (one per image build date) and need a cleanup policy.

**Recommended path.**
1. Fix the current fetcher independently of `importctl`: verify `SHA256SUMS` (and the `.asc` signature if a key is pinned in lxspawn), make extraction symlink-safe, and restore the setuid/setgid/sticky bits that `os.FileMode(header.Mode)` drops.
2. Prototype `importctl pull-tar --verify=checksum` for the btrfs and directory backends on the test host, behind a flag.
3. Decide how to do the privileged rootfs writes (I1) before switching the default. One candidate is running them inside the container's own namespaces through a tightly constrained `systemd-nspawn --pipe` sudo rule, which avoids host-side path resolution; the sudoers regex approach from the first half of this document would apply to it.

**Not verified.** Whether the LXC signing key is already in systemd's vendor keyring (I suspect not), how the LXC server's ETag behaves with the cache, how hosts running systemd 256/257 extract tars (I read main), and how tightly polkit can scope `import1.pull`.

## Spec review (`SPEC.md` and its Lima origin)

Compared `SPEC.md` with Lima's current `templates/default.yaml` (provision and probe documentation) and with the lxspawn code. Verdict: the Lima-derived provisioning layer (modes, `file` with `digest`, `owner`/`permissions`/`overwrite`, `yq`, `param`, probes with `hint`, the template variables) transfers well to nspawn. The VM-specific parts of Lima (images by architecture, mount types, port forwarding through a guest agent, ssh, containerd) were rightly left out. The gaps are in behaviour and in spec/code agreement, not in the shape of the spec.

**Where Lima's model does not transfer**
- **S1. `user` mode has no user to run as (confirmed).** Lima creates a guest user matching the host user and mounts its home, so `{{.User}}`, `{{.UID}}` and `{{.Home}}` make sense there. In lxspawn, `user` mode runs `su - <host username> -c '<script>'` (`provision/exec.go:61-64`) and nothing creates that user inside the container; `BindUser=` is not used anywhere. On a stock image `su` fails with an unknown user unless an earlier `system` step created one. `{{.Home}}` is a host path that means nothing inside the container. Options: use nspawn's `BindUser=` (`--bind-user=`, available since systemd 249), which exposes the host user in the container and binds its home; add an explicit `user:` field to the step and create that user; or drop `user` mode. Also quote the user name in the `su` command.
- **S2. Lifecycle semantics are undefined.** Lima runs every provision step on every boot and tells authors to write idempotent scripts (`data` has `overwrite` defaulting to `true`, "on every boot"). lxspawn runs `system`/`user` steps only from `launch` and `provision`, never from `start` (`manager.go:219-250`, `:629`), and skips unchanged scripts by hash (`engine.go:147-150`). That is a different contract and the spec never states it, which is how the docker-host template ended up starting `dockerd` by hand (T8). Add a "Lifecycle" section: which commands run which modes, the ordering (Lima documents `boot`, then `dependency`, `data`, `yq`, `system`, `user`), whether scripts must be idempotent, and the rule that provisioning must leave services self-starting through systemd units.
- **S3. No composition.** Lima templates can import a `base:` template; lxspawn templates cannot, hence the identical masking/boot boilerplate in all 11 (X2). A small `base:`/`include:` mechanism, or built-in defaults in image post-processing, removes the duplication.

**Where the spec and the code disagree**
- **S4. `boot` is described two ways (confirmed).** The table at `SPEC.md:569` says "early setup before systemd starts", yet the same cell says it is run "by a oneshot systemd service on first boot". Those cannot both be true. In Lima, `boot` runs early in the guest on every boot (cloud-init `bootcmd`). Pick one definition and make the code match it (see R11, where the enable symlink dangles).
- **S5. The DNS workaround section may document a bug.** `SPEC.md:575-594` says masking `systemd-resolved` in `boot` mode "doesn't prevent it from overwriting DNS configuration" and prescribes a post-boot overwrite. If the boot service never runs (R11), that is the true cause, and the spec is recording a workaround for an implementation bug. Re-test after fixing R11.
- **S6. Documented guarantees the code does not enforce.** HTTPS-only for `file` URLs (R24, `http://` is accepted and redirects are followed), `yq` "not supported" expressions (R25, silently ignored instead of an error), and `owner`/`permissions`/`overwrite` (the P3 file-mode finding: modes ignored on existing files, `chown` failures only warn). Either enforce each or soften the spec; a spec that over-promises is worse than a short one.
- **S7. Probes lost Lima's timeout.** Lima's own probe example wraps the loop in `timeout 30s bash -c "until …"`. The SPEC sample and the templates use a bare `until … done`, and the engine adds no per-attempt timeout (X1). Document that probe scripts must terminate, and make the engine enforce it.
- **S8. Parsing is non-strict (R10).** Anyone pasting a Lima template (`images:`, `mounts:`, `vmType:`) gets those fields silently ignored. Decode with `KnownFields(true)` so unknown fields are an error.

**Where lxspawn improved on Lima (keep):** Lima states that the `file` `digest` is "currently unused"; lxspawn verifies it. The host-side `hooks` and the `security`/`gpu`/`network` sections have no Lima equivalent and suit nspawn.

**Recommended spec changes**
1. Add a "Lifecycle and semantics" section (S2, S4, S7).
2. Add a "Differences from Lima" section listing what was dropped and what changed (S1, S2, S8), so users do not assume Lima templates work.
3. Resolve `user` mode (S1) before the 1.0 spec is called stable.
4. Do a spec/code audit pass (S5, S6) once the R-series fixes land, then lock the spec.

## Cockpit plugin: CLI gaps to close first

Compared what the plugin calls (`cockpit/src/api/lxspawn.ts`, `types.ts`, the polling in `MachineList.tsx` and `MachineDetailsPage.tsx`) and what `cockpit/COCKPIT-MACHINES-ANALYSIS.md` plans, against the actual CLI flags and JSON schemas (`cmd/lxspawn/*.go`, `internal/output/schemas.go`). `JSON-API-COVERAGE.md` ends with "All JSON API prerequisites for Cockpit UI are complete!", but that document only checked that each command exists and emits JSON, not that the flags, semantics and data the UI needs are there. Items marked **(confirmed)** were checked in the source. The TypeScript in `cockpit/src` was only read for its API calls; it has not had a full review.

### Plugin calls that fail today (confirmed)

| Plugin call | Problem |
|---|---|
| `createSnapshot` passes `--description` (`lxspawn.ts:198-204`) | `snapshot` defines no flags at all (`cmd/lxspawn/snapshot.go`, `ExactArgs(2)`), so any snapshot with a description fails with "unknown flag". `SnapshotJSON` has a `description` field, but no code in `internal/snapshot` ever stores one. |
| `editResources` passes `--memory-high` (`lxspawn.ts:83`) | `edit-resources` only defines `--cpus`, `--memory`, `--swap`, `--tasks` (`edit_resources.go:111-114`). Setting a soft limit fails with "unknown flag". There is also no `--io-weight`. |
| `editVolume` passes `--readonly`, `"true"/"false"` as two arguments (`lxspawn.ts:128-130`) | `--readonly` is a boolean flag, and cobra does not accept a space-separated value. The `"true"`/`"false"` becomes a second positional argument and `edit-volume` (`ExactArgs(1)`) rejects it. Toggling read-only never works. Plugin fix: pass `--readonly=true` / `--readonly=false`. |
| `editNetwork` only sends mode/bridge/interface | `edit-network` has no `--zone` and no ports flag (`edit_network.go:106-108`), so zone mode and port forwarding cannot be edited from the UI at all. |
| All edit dialogs | The CLI `edit-*` commands only rewrite the source YAML and never regenerate unit files (R9), so even successful calls change nothing. |
| `types.ts` `state: "creating"` | The CLI never emits a `creating` state (no such string anywhere in `cmd`/`internal`). |

### Gaps, by priority

**P1. Needed before the MVP dialogs can work**

- **C1. One declarative "apply" command instead of many `edit-*` commands.** The plan needs edit dialogs for resources, network, volumes, security, GPU, hooks and advanced settings, but the CLI only has edit commands for the first three, and `lxspawn edit` rebuilds the machine from scratch (R1). Rather than adding five or six more flag-based commands, add `lxspawn apply <name> [-f -]` that takes the full config (YAML on stdin), validates it, diffs it against the current config, regenerates the `.nspawn`, slice, drop-in and hooks in place (keeping the rootfs), runs `daemon-reload`, and returns JSON describing what changed and whether a restart is needed. It supports `--dry-run` for a preview. This matches the project's declarative/GitOps philosophy, and the UI reads `config --json`, edits fields in a form and sends the whole object back. The existing `edit-*` commands can become thin wrappers or be deprecated.
- **C2. Report `restart_required`.** cockpit-machines shows a "needs shutdown" indicator for pending configuration changes (the analysis doc lists it). Record a hash of the applied vs running configuration, and return `restart_required` (and `pending_changes`) from `apply`, `status` and `list`.
- **C3. `config --json` is missing most of the data the UI needs (confirmed).** `ConfigData` has no `hooks`, `provision`, `param`, `probes`, `journal`, `security.private_users`, `security.system_call_filter` or GPU details beyond `enabled`/`type`/`devices`, although `types.ts` expects hooks/provision/param/probes. `ResourceJSON` also omits `memory_high` and `io_weight`, so the Edit Memory dialog cannot show current soft limits. Make `config --json` return the full parsed schema.
- **C4. Store a canonical copy of the config inside lxspawn's state.** `create` records only `SourcePath` (`manager.go:183`, `create.go:41`) and `status`/`config` re-parse that file every time (`manager.go:494-495`). If the file is moved or deleted, or a relative path is stored, they break. That is why the plugin currently writes YAML into `~/.local/share/lxspawn/<name>/config.yaml` itself. Copy the config into `/var/lib/lxspawn/<name>/config.yaml` on create and apply, and make that the source of truth, so the UI never has to manage files.
- **C5. Create flow.** The wizard currently builds YAML client-side (string-replacing the template name) and writes it to a file before running `launch`. Add: `create -`/`launch -` (config on stdin), `create --template NAME --name N --param k=v` so templates and parameters are handled by the CLI, and a working `validate`/`--dry-run` that returns structured errors (see C9). `validate` must call the real validation first (R10).
- **C6. Templates are not installed (confirmed).** `make install` installs only the binary (`Makefile:22-23`). `list-templates` searches `/usr/share/lxspawn/templates`, `/usr/local/share/lxspawn/templates`, `~/.local/share/lxspawn/templates` and a cwd-relative `examples/templates`. Under Cockpit the working directory is the user's home, so on a fresh install the wizard shows no templates. Embed the templates in the binary (`go:embed`) or install them, and add install targets for polkit and the Cockpit plugin (`/usr/share/cockpit/lxspawn`).
- **C7. Per-user machine registry (R13).** The CLI reads `~/.local/share/lxspawn/machines.json` (`deploy/state.go:33`). Cockpit runs commands as the logged-in user, so two admins, or one admin switching to superuser, see different lists. Move the registry to `/var/lib/lxspawn`.

**P2. Needed for the planned cards and dialogs**

- **C8. Missing lifecycle operations.** Add `stop --force`, `restart` (and/or `reboot`), and autostart (`lxspawn autostart <name> on|off`, backed by enabling `systemd-nspawn@<name>.service`), with `autostart` and `restart_required` in `list`/`status`. The analysis doc plans Force stop, Reboot and an Autostart toggle, none of which exist.
- **C9. Stable error and validation format.** Every failure is reported as `COMMAND_FAILED` (`main.go`, `output.PrintError`), and the plugin only shows stderr text. Define error codes (`MACHINE_NOT_FOUND`, `MACHINE_RUNNING`, `PERMISSION_DENIED`, `VALIDATION_FAILED`, ...), return field-level validation errors (`{"field": "volumes[0].host", "message": "..."}`), and use distinct exit codes.
- **C10. Progress for long operations.** Creating a machine downloads and extracts a rootfs and can run provisioning for minutes (download timeout 30 minutes), but the CLI gives a UI nothing to show. Add a progress/event stream (for example `--progress=json`, newline-delimited events: `downloading`, `extracting`, `provisioning`, `probe`, `done`), a real `creating` state with an operation lock so the UI can disable actions, and a way to cancel.
- **C11. Version and health information.** Add `lxspawn version --json` and `lxspawn doctor --json` (lxspawn and API version, systemd version, storage backend, group membership, polkit/sudoers installed, nftables present). The envelope already carries `version: "1.0"` but the plugin ignores it. Cockpit can use `doctor` for an onboarding screen when the user is not in the `lxspawn` group.
- **C12. Snapshot semantics.** Add a description parameter and store it; expose `requires_stopped` (or refuse with `MACHINE_RUNNING`, R18); fix `created_at` (it is the directory mtime, P3); make sure rollback no longer deletes the other snapshots (R2). The Revert dialog's warning has to match what rollback actually does.
- **C13. Logs for a log viewer.** `logs --json` returns the host unit log while text mode follows the container journal (R23), and `--lines` works only in JSON mode. The plugin has no logs call yet. Make both modes read the same source, add `--since`/`--priority`, and add a streaming follow mode usable through `cockpit.spawn`.

**P3. Efficiency and polish**

- **C14. Batched stats.** `MachineList` calls `stats` once per machine every 5 seconds (`MachineList.tsx:151-168`), spawning one process per machine, each sampling CPU for 100 ms (`manager.go` `readCPUUsage`). Add `stats --all --json` (or `list --json --stats`), and return cumulative counters with a timestamp (`usage_usec`, memory) so the UI computes rates from consecutive samples without the CLI sleeping. For live state changes, the plugin can subscribe to machined's D-Bus signals through `cockpit.dbus` instead of polling.
- **C15. Smaller:** `getTemplateContent` runs `list-templates` a second time just to find a path (add `list-templates --show NAME`); distro list is hard-coded (`list_distros.go:20-21`) and could be checked against the image server; "preserve volumes on delete" in the plan is moot because volumes are host bind mounts (confirm and drop the option); clone, rename and description are low-priority but need CLI support first.

### Suggested approach

1. Fix the failing plugin calls above (three of them are one-line plugin changes).
2. Land C1 (`apply`), C2, C3, C4 together, since the edit dialogs depend on all four, and fix R1/R9 as part of it.
3. C5, C6, C7 so the create wizard and the machine list work on a clean install for any user.
4. C8-C13 as the matching cards are built; C14 once a few machines make polling visibly slow.
5. Update `JSON-API-COVERAGE.md`. Its conclusion ("complete") is out of date, and a per-endpoint test that runs each documented plugin call against the real CLI (exactly the check that would have caught the failing flags above) would keep it honest.

## First-run experience

Why this matters: nspawn is easy to give up on before the first machine runs, and lxspawn's job is to remove that wall. Today a newcomer has to do all of this before seeing anything work: get the binary, `sudo lxspawn setup`, add themselves to the `lxspawn` group, log out and back in, write a YAML file, and run `launch`. Each step is a place to quit, and the forced logout is the worst, because it comes before they have seen a single success.

**What exists (confirmed).** `.goreleaser.yml` builds Linux `amd64` and `arm64` tarballs with a `checksums.txt`, and the archives include the README, SPEC, examples and templates. The README's Installation section still says only "Build from source" (`README.md:17-25`), and `launch` takes exactly one argument, a YAML file (`launch.go:14-16`, `ExactArgs(1)`). deb, rpm and brew packages are planned for later.

**F1. One-command first machine.** Allow `lxspawn launch debian:bookworm [name]` (and `create`) with sensible defaults, no YAML. Treat the YAML as the power-user path. This is the same mechanism as the `create --template NAME` item in the Cockpit section (C5); build it once and let both use it.

**F2. Setup that ends with a verified result.** `lxspawn setup` should finish by running the same checks as the planned `lxspawn doctor` (C11): group exists, user is in it, polkit and sudoers files installed and valid, nspawn and machined present, storage backend detected, nftables present for private networking. For anything left to do, print the exact next command. Add `lxspawn doctor` to the quick start so users can check themselves.

**F3. Avoid the logout step where possible.** After `usermod -aG lxspawn $USER`, the new group does not apply to existing sessions. Document `newgrp lxspawn` (or `sg lxspawn -c "lxspawn ..."`) as a way to continue immediately, and have `setup` print it. Consider making `setup` accept `--user NAME` so it can do the group step itself when run with sudo, since it already knows `SUDO_USER`.

**F4. Make the tarball installable.** Extracting the release archive leaves a binary in a download directory, which `sudo lxspawn setup` cannot find unless it is on root's `PATH`, and the bundled templates are only found through the cwd-relative `examples/templates` fallback (C6). Either add an `lxspawn install` subcommand (copies the binary and templates to `/usr/local/...`) or ship a short `install.sh`, and update the README to lead with the release download, with building from source as the alternative. Verify the checksum in the install instructions (`sha256sum -c checksums.txt`).

**F5. A quick start that is tested, not just written.** Make the README's first section: download, install, `setup`, `launch`, `shell`, `delete`, nothing else. Run it on clean Fedora, Debian and Ubuntu VMs, time it (target: a running shell in under five minutes), and keep that sequence in CI (see the testing recommendation in the first half). Move the long configuration reference below it or into `SPEC.md`.

**F6. Errors that say what to do.** The most likely first failures are: user not yet in the group, nspawn not installed (it is in a separate package on Debian, Ubuntu and Fedora), a non-systemd host, and no network access to the image server. Detect each early and print a one-line fix (`apt install systemd-container`, `newgrp lxspawn`, ...) instead of a raw command error.

**F7. Packaging later (deb, rpm, brew).** When you add packages, let them run `setup` as a post-install step or at least create the group and install the polkit/sudoers files, so the package gives a working install. Note that brew only applies to Linux (Homebrew on Linux); the tool has no macOS target. Also decide where templates and the Cockpit plugin live in the packages (`/usr/share/lxspawn/templates`, `/usr/share/cockpit/lxspawn`) and make the binary look there first.

## Suggested order of work

1. Decide the trust model (root-equivalent group or locked-down directories) and fix section 6, since it determines how much of the rest matters.
2. R1, R2, R3, R4: the data-loss and traversal bugs. They are small, local fixes.
3. R9, R10: make the edit commands apply their changes and make `validate` honest.
4. R5, R6, R7, R8: symlink-safe extraction and writes, and escaping in the compiler.
5. Sudoers regex rules and the `nsenter` replacement from the first half of this document.
6. R11 onward, then CI and test gaps.
7. Templates: X1 (probe timeouts, an engine fix that affects every template), then T1 (Nextcloud data loss), T8 (Docker not surviving restart), T11 (open Samba share), X3/X4 (pinned downloads and secrets), and X7 (CI check so templates stop regressing).
8. Cockpit prerequisites (section "Cockpit plugin: CLI gaps"): fix the failing plugin calls, then C1-C4 (`apply`, restart-required, full `config --json`, canonical config copy), then C5-C7 (create flow, installed templates, system-wide registry), before building the remaining dialogs.
9. First-run experience (section "First-run experience"): F1 and F2 first (one-command launch, setup that verifies), then F4/F5 (installable release, tested quick start) before the Reddit post.
